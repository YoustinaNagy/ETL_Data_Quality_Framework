# ETL Data Quality Framework

This project is a compact, Python-based data quality and reconciliation framework built around Apache Spark. Its goal is simple but important: validate that data moved correctly from a source dataset to a target dataset and that the data still satisfies business expectations after the transformation or transfer.

The project is intentionally small, but it follows a realistic ETL testing pattern used in production systems:

- read source and target data into Spark DataFrames
- validate schema and required fields
- check for nulls, duplicates, and invalid ranges
- compare source-to-target rows using a business key
- fail tests when expected data-quality issues are detected
- generate an HTML report for review

---

## Why this framework exists

Many ETL pipelines fail silently because they only check whether a job completed successfully. A job can finish without incident and still produce wrong data. This framework addresses that gap by testing the actual content of the data.

The core idea is:

- source data is the expected truth
- target data is what the ETL pipeline produced
- validations ensure the target is complete, consistent, and trustworthy

---

## High-level flow

```text
config/settings.yaml
        |
        v
pytest fixtures in tests/conftest.py
        |
        v
CsvConnector reads CSV files into Spark DataFrames
        |
        v
Schema / quality / reconciliation validators run checks
        |
        v
Assertions in tests validate expected results
        |
        v
HTML report generated by pytest-html
```

The framework is designed so that each layer has a distinct responsibility:

- configuration holds reusable facts such as file paths and business keys
- connectors turn files into Spark DataFrames
- validators execute check logic
- tests convert these checks into system-level assertions
- reports provide evidence for review and debugging

## File-by-file explanation

### config/settings.yaml
This file stores the project settings used by the tests.

It defines:

- app name for Spark
- source file path
- target file path
- key column(s) used for reconciliation
- required columns for validation

This keeps the framework configurable without hardcoding file names and rules into the test suite.

### data/source/orders.csv
This is the source dataset used as the reference data. It represents the expected state before transfer or transformation.

### data/target/orders.csv
This is the target dataset. It represents the data produced by the ETL process and is compared against the source dataset.

### src/__init__.py
This package initializer marks the src directory as a Python package and provides a natural location for future shared imports or project-level metadata.

### src/spark_session.py
This file creates the local SparkSession used by the entire framework.

It matters because all validation logic runs on Spark DataFrames, and Spark needs a session to execute them. This file centralizes the Spark setup so that tests do not duplicate session creation code.

### src/connectors/csv_connector.py
This connector is the file-reading layer.

It uses Spark to parse CSV files with headers and inferred schema and returns DataFrames. It separates data extraction concern from validation logic, which keeps the framework modular and easier to expand.

### src/validators/schema_validator.py
This module verifies the structural integrity of the datasets.

It checks:

- whether required columns exist
- whether source and target schemas match

Without this step, later comparisons could fail for the wrong reasons, such as column drift or mismatched data types.

### src/validators/quality_validator.py
This module validates each dataset independently for data-quality issues.

It checks:

- null counts in required fields
- duplicate rows based on key columns
- invalid numeric ranges such as negative amounts

These tests are not source-vs-target comparisons; they validate the health of a dataset in isolation.

### src/validators/reconciliation_validator.py
This is the source-to-target comparison layer.

It joins source and target by the business key and classifies records as:

- MISSING_IN_SOURCE
- MISSING_IN_TARGET
- VALUE_MISMATCH

This is the core ETL validation step because it answers the question: “Did the target data match the source data, and if not, what changed?”

### tests/conftest.py
This file defines the shared pytest fixtures used by the suite.

Key fixtures:

- settings: loads the configuration file
- spark: builds a reusable Spark session
- datasets: reads the source and target CSV files into DataFrames

Fixtures are important because they reduce repetition and keep test code readable.

### tests/test_schema.py
This file validates the structural correctness of source and target data.

It checks that:

- all required columns are present
- source and target schemas align

### tests/test_data_quality.py
This file asserts business-rule quality checks.

It verifies that:

- duplicate keys do not exist
- required fields are not null
- numeric columns remain within valid ranges

### tests/test_reconciliation.py
This file checks the most important ETL outcome: whether source and target data align after reconciliation.

The expected discrepancy types are intentionally built into the test so the framework proves it can identify the known defects in the sample data.

### run_tests.sh
This script is the project’s convenience runner.

It creates a reports folder and then executes pytest with HTML reporting enabled, so the results are easier to review outside the terminal.

### reports/
This folder stores the generated HTML test report. The report acts as a readable artifact for stakeholders, QA reviewers, or CI pipelines.

### requirements.txt
This file lists the Python dependencies required by the framework, including PySpark, pytest, pytest-html, and PyYAML.

### pytest.ini
This file is the pytest configuration file. It controls how tests are discovered and run, helping keep execution consistent across environments.

## What the project is proving

This repository demonstrates a simple but realistic ETL quality framework where the validation is based on data content rather than just process success.

The included sample data intentionally contains three known defects:

- order 3: value mismatch
- order 4: missing in target
- order 5: missing in source

These expected defects are used to validate that the framework is correctly detecting changes between source and target data.

---

## Typical execution flow during a test run

1. pytest loads the configuration from settings.yaml.
2. The spark fixture creates a Spark session.
3. CsvConnector reads the source and target CSV files.
4. Schema checks run to confirm expected columns and types.
5. Quality checks look for nulls, duplicates, and invalid business rules.
6. Reconciliation compares rows on the key column and identifies differences.
7. Tests assert expected outcomes.
8. pytest-html generates a readable HTML report in the reports folder.

## Quick start

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
./run_tests.sh
```

The command above creates the local test environment, installs the dependencies, and runs the checks.

---

## Summary

This framework is best understood as a small ETL testing harness:

- connectors read the data
- validators evaluate quality and structure
- reconciliation compares source and target
- pytest turns those checks into executable verification
- HTML reports make the outcome explainable and reviewable

That separation of concerns is what makes the project more than a collection of scripts; it is a repeatable data-quality testing pattern.
